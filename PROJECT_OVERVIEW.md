# OutBox Project Overview

## 1. Project Overview

### What this application does
This repository is a minimal full-stack web app with a Next.js frontend and a separate Express + Prisma backend. The implemented functionality is centered around Google OAuth authentication and a protected dashboard route. The app currently behaves like an auth starter or scaffold rather than a complete business application.

### Main purpose and use cases
The project appears to be designed to support:
- authenticating users with Google
- protecting application routes behind login
- storing session and account data in PostgreSQL
- serving as a foundation for a larger product or dashboard application

The current codebase already demonstrates the core auth flow, but it does not yet contain a large domain feature set beyond the login/dashboard shell.

### Who/what uses it
From the codebase, the application is used by:
- end users accessing the browser app
- a Next.js frontend that renders pages and auth UI
- an Express backend that exposes Better Auth endpoints
- PostgreSQL storing user/session/account data

### Major features
- Google OAuth sign-in
- Session checking with cookie-based authentication
- Protected dashboard route
- Redirect logic for authenticated vs unauthenticated users
- Theme and query providers in the frontend
- Prisma-based auth persistence

### Overall architecture
The architecture is split into two major parts:

- Frontend: Next.js app in the client directory
- Backend: Express server in the server directory

At runtime, the flow is:

User → Frontend → Better Auth API → Prisma/PostgreSQL

The frontend asks Better Auth for session status and decides whether to allow access to protected pages.

## 4. Architecture

### High-level architecture
The application is structured as a multi-app monorepo-like setup with a frontend and backend separated at the top level.

The architecture is:

User -> Next.js frontend -> Better Auth backend -> PostgreSQL

### Important flows

#### Authentication flow
1. User arrives at the app and hits the login page.
2. The frontend calls Better Auth signIn.social for Google.
3. Better Auth redirects to Google.
4. Google returns the user to the configured callback.
5. Better Auth creates/updates the user and session in Postgres.
6. Future requests check session state through /api/auth/get-session.

#### Protected route flow
1. Server-side calls in getSession read the Cookie header.
2. The app fetches /api/auth/get-session.
3. If no valid user exists, redirect to /login.
4. If valid, the page renders.

#### Dashboard flow
1. Authenticated user lands on /dashboard.
2. requireAuth verifies session.
3. If valid, the dashboard page renders.

## 12. Data Flow

### User registration/login
1. User clicks Continue with Google.
2. The client calls Better Auth social sign-in.
3. Better Auth handles Google OAuth flow.
4. A new user/session is created in the database.
5. The app checks session state and redirects to /dashboard.

### Protected page access
1. Frontend calls getSession.
2. Cookie is sent to /api/auth/get-session.
3. If session is present, page renders.
4. If not, redirect to /login.

### Logout
1. The sign-out button calls Better Auth signOut.
2. Client redirects to /login.

## 16. Important Architectural Decisions

- The app is split into frontend and backend directories.
- Authentication is centralized in Better Auth instead of custom auth implementation.
- Prisma is used to persist Better Auth tables rather than defining separate user business models.
- Route protection is minimal and boolean-based.
- The project is a starter structure for social auth and dashboard gating.

These decisions make the app easy to extend, but they also mean the codebase currently lacks deeper domain logic and production hardening.
